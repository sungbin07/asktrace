# asktrace 제품 방향 제안

이 문서는 현재 코드와 README를 바탕으로 한 제품 가설이다. 사용자 인터뷰나 사용량
실험으로 검증된 결론은 아니다. 아래의 피드백 카드, 분류, 명령어는 제안이며,
이번 변경에서 구현한 기능은 Codex 로컬 대화 수집이다. 최신 main에는 Claude Code
자동 수집 훅과 기본 SVG 잔디도 추가됐다. 질문의 연속성과 지식 잔디에 관한 후속 제안은
[질문 여정과 사고의 변화](QUESTION_JOURNEYS.ko.md)에 정리했다.

## 추천하는 약속

**“AI와 나눈 대화에서, 내가 익힐 것과 다음 작업을 더 잘 맡기는 방법을 찾는다.”**

영문 소개 후보:

> Turn your AI conversations into better judgment and better workflows.

첫 사용자층은 Codex나 Claude Code를 매일 사용하고, 반복되는 수정 지시와 시행착오를
줄이고 싶은 개인 개발자로 좁힌다. 이들은 로컬 기록이 있고 CLI에도 익숙해,
새 대화 습관을 요구하지 않고 지난 작업에서 가치를 보여줄 수 있다.
일반 AI 사용자는 이후 ChatGPT·Claude 내보내기를 통해 확장한다.

README 첫 화면에서는 설치 명령과 함께 근거가 붙은 피드백 카드 한 장을 보여준다.
현재의 질문 수·개념 수·숙련도 표만으로는 사용자가 무엇을 바꿀지 판단하기 어렵다.

## 현재 기반과 신뢰를 위해 바꿀 부분

이미 갖춘 기반은 로컬 SQLite, 오프라인 실행, 중복 없는 가져오기,
여러 대화 소스, 교체 가능한 태거, Markdown/JSON 보고서다.
여기에 Codex 로컬 기록 수집이 추가됐다.

다음은 제품 메시지와 지표를 바꾸기 전에 해결할 문제다.

- `mastery`는 질문의 깊이, 등장한 날짜 수, 최근성을 이용한 추정치다.
  설계를 요청했다고 설계를 이해한 것은 아니므로 이를 검증된 숙련도로 표현하지 않는다.
  당장은 “다뤄본 주제와 질문의 변화”를 보여주고, 이해도는 별도의 짧은 설명·문제 풀이로
  확인하는 편이 타당하다.
- 같은 질문의 반복은 망각, 의도적 위임, 다른 프로젝트의 문제, 실패한 답변에 대한
  재요청일 수 있다. “잊어버렸다” 대신 “반복이 감지됐다”라고 표시하고 목적을 확인한다.
- 한국어·영어 표현과 동의어를 같은 개념으로 묶어야 반복 피드백이 성립한다.
  현재 오프라인 태거는 표면 단어를 추출하므로, 개념 병합과 사용자 정정이 중요하다.
- 현재 저장 모델은 질문과 태그 중심이다. 프로젝트, 도구 실행 결과, 작업 완료 여부를
  충분히 저장하지 않으므로 시간 절감, 생산성, 실패 원인을 단정할 근거가 없다.

## 도움이 되는 피드백

모든 피드백은 **관찰 → 원문 근거 → 가능한 해석 → 작은 행동 → 사용자 확인**으로 구성한다.
첫 보고서에서는 근거가 있는 제안 최대 세 개만 보여준다.
자료가 부족하면 억지로 제안을 채우지 않는다.

| 사용자 상황 | 보여줄 관찰 | 다음 행동 | 잘못된 판단을 고치는 방법 |
| --- | --- | --- | --- |
| 개념을 직접 익히고 싶다 | 같은 개념을 여러 날 다시 질문했다 | 자기 말로 설명할 질문 하나와 관련 과거 대화 제공 | “복습 필요” 또는 “외울 필요 없음” |
| 에이전트에 같은 규칙을 반복한다 | 여러 작업에서 같은 수정 지시가 등장한다 | 프로젝트 범위를 표시한 AGENTS.md·스킬·체크리스트 초안 | 일회성 지시인지 상시 규칙인지 확인 |
| 작업 요청 후 여러 번 정정한다 | 첫 요청과 후속 정정에서 빠진 조건이 드러난다 | 다음 요청에 넣을 완료 조건 초안 | 정정이 요구 변경이었는지 확인 |
| 팀이나 프로젝트가 바뀌어 다시 묻는다 | 비슷한 개념이 다른 맥락에서 등장한다 | 프로젝트별 참고 메모로 분리 | 다른 문제로 표시하거나 개념 병합 취소 |
| 학습 진전을 확인하고 싶다 | 사용자가 고른 목표의 질문과 복습 답변이 축적됐다 | 이전 설명과 지금 설명을 비교 | 점수 근거와 평가 오류를 수정 |

예시 카드 — 실제 사용 결과가 아닌 설명용 예시:

> **다음 작업에 남겨둘 규칙이 있습니다**
>
> 지난주 세 세션에서 “기존 API 응답 형식을 유지해 달라”고 요청했습니다.
> 관련 발언 세 개를 확인할 수 있습니다.
>
> 이 조건이 프로젝트의 상시 규칙이라면 다음 초안을 검토해 보세요.
> “API 응답 스키마를 바꿀 때는 호환성 영향을 확인하고 계약 테스트를 실행한다.”
>
> 선택: 프로젝트 규칙으로 저장 / 이번 작업에만 해당 / 잘못 묶인 대화

초안은 검토 후 사용자가 적용한다. 대화에서 추출된 문장이 스스로 실행 권한을 갖거나
자동으로 에이전트 지침 파일을 바꾸게 하지 않는다.

## 하네스와 연결하는 방식

수집과 행동을 나눠 단계적으로 만든다.

1. **현재:** Codex·Claude Code의 사용자 입력을 같은 질문·태그 모델로 가져온다.
   Codex 소스는 로컬 JSONL을 읽으며 Codex를 분석 모델로 호출하는 기능은 아니다.
2. **다음:** 프로젝트와 사용자 의도(이해·위임·문제 해결), 근거 질문 ID를 기록하고
   주간 피드백을 생성한다. 지시 재사용 후보는 질문 텍스트만으로도 제안할 수 있지만,
   실패 원인이나 실제 개선 효과는 사용자 확인이 필요하다.
3. **이후:** 사용자가 선택한 범위에서 명령 종료 상태, 테스트 결과, 완료 확인 등의
   이벤트를 수집한다. 사용자 발언, 하위 에이전트 작업, 시스템 입력을 분리한다.
   이 단계에서 비로소 같은 작업 유형의 재시도 패턴을 조사한다.

향후 진입 명령 후보는 `asktrace review --last 7d`다.
최근 기록을 동기화하고, 새 질문만 태깅하며, 근거가 있는 피드백 세 개를 보여주는
한 번의 흐름을 목표로 한다. 아직 구현된 명령은 아니다.

Codex를 태거로 쓰는 어댑터는 이후 추가할 수 있다. 먼저 기존 태거 인터페이스에 맞춰
구조화된 출력과 오류 처리를 검증한다. 로그를 읽을 권한과 유료 모델 호출 권한은
별개로 취급한다. MCP 서버는 실제로 에이전트가 보고서를 요청해야 할 때 추가한다.

## 공개와 GitHub 스타

첫 공개에서 보여줄 장면은 “설치 → 내 기록 분석 → 바로 적용할 개선 한 가지”다.
스타를 얻는 접점과 재사용을 만드는 접점을 함께 만든다.

- README 상단에 30초 데모, 완성된 피드백 카드, 로컬 처리 범위를 표시한다.
- 계정과 API 키 없이 실행할 수 있는 샘플을 유지한다. 개인 기록을 읽기 전에도
  어떤 결과를 받는지 확인할 수 있어야 한다.
- 공유용 주간 카드는 명시적 선택으로 생성하고 원문, 경로, 저장소명은 기본 제외한다.
  개념명도 민감할 수 있으므로 내보내기 미리보기에서 확인·수정할 수 있게 한다.
  개인별 숙련도 순위 대신 사용자가 선택한 발견과 적용한 개선을 보여준다.
- Codex·Claude Code 사용자 커뮤니티에는 실제 사용 사례와 검증 범위를 공개한다.
  홍보 문구보다 “반복하던 지시를 어떤 규칙으로 바꿨는지”를 보여준다.
- 소스별 형식 설명과 합성 fixture를 제공해 Cursor 등 새 어댑터를 기여하기 쉽게 한다.
  여러 소스를 한꺼번에 추가하기보다 첫 두 소스의 분석 품질을 먼저 확인한다.

## 실행 순서와 검증

아래 숫자는 초기 실험을 위한 제안 기준이다.

| 순서 | 만들거나 확인할 것 | 판단 근거 |
| --- | --- | --- |
| 1 | 개인 개발자 10명에게 기존 보고서와 근거 카드 시안을 보여주기 | 자기 기록에서 정확하다고 인정한 발견이 있는가 |
| 2 | 개념 정정·병합, 반복의 목적 확인, 근거 질문 연결 | 잘못 묶인 개념과 잘못된 반복 해석이 줄어드는가 |
| 3 | 주간 피드백과 사용자가 적용할 규칙 초안 | 10명 중 5명 이상이 실제 행동 하나를 선택하는가 |
| 4 | 첫 실행 단순화와 선택형 공유 카드, 데모 공개 | 첫 보고서 완료율과 공유를 통한 새 사용자가 생기는가 |
| 5 | 다음 주 재사용과 결과 확인 | 자발적으로 다시 실행하고 제안의 효용을 확인하는가 |

주요 제품 지표는 “주간 보고서를 본 활성 사용자 중 제안 하나를 유용하다고 확인하고
적용한 비율”과 다음 주 재사용률로 둔다. 스타는 유입·관심 지표로 따로 추적한다.
모수와 수집 범위를 함께 기록하고, 초기에는 참여자의 동의를 받은 인터뷰나 설문으로
측정한다. 로컬 도구에 자동 사용량 수집을 전제로 넣을 필요는 없다.

제안을 적용한 뒤 반복이 줄어들어도 바로 생산성 향상이라고 결론내리지 않는다.
작업량과 난이도가 바뀌었을 수 있으므로 사용자의 확인과 비교 가능한 작업 근거를
함께 본다. 예쁜 개념 지도, 팀 대시보드, 리더보드는 이 핵심 효용이 확인된 뒤 검토한다.
